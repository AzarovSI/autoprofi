## Инциденты и уроки

Формат: что случилось → причина → как исправили. **Урок** — правило на будущее.

**WB: «Продажи, ₽» и «Налог» читались из чужих колонок (найдено 14.10).**
Во всех периодах MPPROFIT WB `sales_gross` содержал «Заказы шт.», а `tax` — «Налоговую базу»
(сентябрь: 24 149 вместо 73,6 млн и 46,3 млн вместо 0). Причина: шапка двухуровневая, индекс
заголовков брал строку 4 (секции) раньше строки 5 (метрики), а секции «Продажи» и «Налог»
совпадают с именами метрик. На экраны не попадало: `tax` выводил только экран «Обзор недели»,
которого нет в меню. Исправление: у WB индекс сначала по строке 5, плюс сверка с ИТОГО при каждой
загрузке (`cd12eca`). Ozon пока не проверен: его алиасы нарочно опираются на имена секций.
**Урок:** колонку, найденную по имени, сверять с ИТОГО отчёта — совпадение имени не гарантирует,
что прочитана нужная колонка.

**Недоступна зона ru-central1-b Yandex Cloud (с 08.10, на 09.10 10:41 МСК не восстановлено).**
С 08.10 01:31 МСК не отвечают кластер БД `avtoprofi-db` и VM `autoprofi-web`.
Оба стоят в зоне b, у кластера один хост. Вместе с АВТОПРОФИ остановлен azarov_capital
(та же БД). vilka (зона a) работает. Сайт на Perplexity (autoprofi.pplx.app) отвечает
на `/health`, но этот адрес к БД не обращается.
Причина на стороне Яндекса (status.yandex.cloud, апдейт 08.10 15:19): пожар в дата-центре
в Сасово после атаки БПЛА, ДЦ полностью остановлен. По оценке Яндекса (08.10 18:25), быстро
зону не вернут. Яндекс советует восстанавливать сервисы в других зонах, создание новых
ресурсов может быть ограничено.
Состояние копий:
- автоматические копии Managed PostgreSQL есть, но восстановить их в новый кластер
  в другой зоне не удаётся (08–09.10). При восстановлении в `ru-central1-d` консоль отвечает
  `cannot allocate resources` (HTTP 500, grpcCode 13). Параметры попытки: класс `b2.medium`,
  network-ssd 20 ГБ, один хост. 09.10 владелец перебрал разные зоны и классы хостов,
  везде та же ошибка. Это совпадает со словами Яндекса об ограничении на создание
  новых ресурсов;
- на Google Диске (бэкапы Perplexity и `autoprofi_backups`) только архивы кода, дампа данных нет;
- копии базы на Mac нет: копирование настроили 08.10 в 15:13, уже во время сбоя,
  и первая попытка упала по таймауту;
- есть только структура (`db/schema_public_20261007.sql`) и архив кода.

Пока не исправлено. **Урок:** база в одной зоне на одном хосте и без внешней копии данных
останавливается вместе с зоной. Варианты защиты — в `docs/backlog.md` («Отказоустойчивость»).

**Дневной файл Ozon затирал чужие поля (13.07).**
После перезагрузки дня пропадали реклама, CTR, отзывы, рейтинг и остатки 1С.
Причина: загрузчик удалял строки дня и вставлял заново только свои колонки.
Исправление: `PRESERVE_COLS` в `ozon_daily_loader` (позже в `wb_daily_loader`
и `ya_daily_loader`). Данные за 07–09.07 пришлось перезагрузить из исходных отчётов.
**Урок:** при перезаписи дня сохранять поля других загрузчиков.

**Ошибка 524 и «Failed to fetch» при загрузке файлов (10.07, 14.07, 28.07, 14–15.09).**
Загрузка обрывалась, данные не записывались, потому что транзакция откатывалась.
Причина: построчные SQL-запросы к облачной БД, сотни и тысячи обращений.
Прокси обрывал запрос примерно через 100 секунд.
Исправление: `executemany`, `UPDATE … FROM (VALUES …)`, один `INSERT … SELECT … ON CONFLICT`.
Дневной Ozon ускорился с 242 до 7 с, рейтинг WB — с 61 до 2,5 с, цены — с 50–70 до 2,5 с.
**Урок:** каждое обращение к Yandex Cloud дорого, загрузчики пишут только пакетно.

**Медленное открытие разделов (июль, точная дата неизвестна).**
Справочник открывался около 12 секунд. Причина: на каждый запрос открывалось новое
