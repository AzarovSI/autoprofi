# Бизнес-правила и формулы

Обновлено: 07.10.2026. Источник: выгрузка Perplexity (05, 03) + сверка с кодом. При расхождении верить коду и тестам.

Как читать: у каждого правила указано, где оно реализовано (`файл:функция`, для вложенных
функций — `внешняя.внутренняя`), и какой тест его защищает. «Тестов нет» — правило держится
только на коде; менять его осторожно и с ручной сверкой на данных.

## Глоссарий

| Термин | Значение в этом проекте |
|---|---|
| РНП | Ежедневный управленческий отчёт по товарам (в обиходе «рука на пульсе»). В меню «РНП» = дневные заказы (`rnp_sales_router`, view `rnp_sales`). Раздел «Юнит-экономика» исторически тоже называется РНП в коде (`rnp_router`, `/api/rnp`, view `rnp`), а ключ метрики `rnp` там = маржинальность (прибыль / выручка). Не путать. |
| Pi кабинета площадки | «Индекс цены, Pi» (`price_index_pi`). Ozon — из дневного файла заказов; WB — из отчёта «Индекс цен» ЛК: цена товара WB / цена идентичного товара (`app/wb_pi_loader.py`). Только на уровне товара. |
| «Базовая цена, Pi» | Дневной Pi к базовой цене своего МП из `price_index_daily` (`wb_base_pi` / `ozon_base_pi`). Числитель — загружаемая цена, а для L1 с «АВТОПРОФИ» — цена покупателя. |
| «Pi покупатель» | Цена покупателя Ozon / цена покупателя WB (`buyer_pi`). Один и тот же коэффициент в РНП Ozon и РНП WB, для WB не инвертируется. |
| Pi прайс-листа | В «Цены → Прайс-лист»: базовая Ozon / базовая WB и базовая Yandex / базовая WB. Без раскраски. Четвёртый, отдельный смысл Pi. |
| СПП / соинвест | Скидка площадки (WB — СПП, Ozon — соинвест). Хранится долей 0..1 (`spp_pct`). `spp_rub` есть только у Ozon. |
| ДРР (три смысла) | 1) РНП заказы: `drr_total_pct` = расходы на рекламу / сумма заказов за ячейку. 2) Юнит-экономика: «Продвижение, от продаж» = реклама / выручка и «Продвижение, от заказов» = реклама / заказы руб.; плюс старое `drr_pct` с подписью «ДРР % к заказам», которое на деле = `promo_total` / выручка (знак Ozon отрицательный, у WB = 0). 3) ABC: реклама / выручка за выбранные месяцы. |
| Выкуп | Юнит-экономика: `buyout_pct` из MPPROFIT, агрегируется взвешенно по выручке. В РНП WB `buyout_qty`/`buyout_rub` хранятся, но не показываются. |
| MPPROFIT | Сервис, из которого вручную выгружаются недельные/месячные отчёты юнит-экономики (`fact_weekly`, `fact_monthly`). |
| PriceVA | Мониторинг цен конкурентов: средняя и минимальная цена конкурентов на выбранную пользователем дату (в файле даты нет). |
| Базовая цена | Управленческий ориентир по паре артикул+МП (`catalog_base_prices`, история — `catalog_base_prices_hist` с `valid_from`/`valid_to`). Целое число; пусто = удалить. |
| Загружаемая цена | Цена продавца. В разделе «Цены» и в Pi — из прямого ценового отчёта (`mp_price_daily.upload_price`; Ozon — «Цена продавца после акций»). В РНП заказы «Ср. загружаемая цена» = сумма заказов / заказы шт. Это разные источники. |
| Цена покупателя | Цена после СПП/соинвеста. В прямых отчётах берётся из файла; в старых строках `mp_price_daily` — загружаемая × (1 − СПП), округление до копеек; в РНП заказы — ср. загружаемая × (1 − СПП ячейки). |
| Общие удержания (`noart_exp`) | Строки `row_type='Общие удержания'` в `fact_weekly`: расходы МП без привязки к артикулу. Только в корне «Итоги». |
| Нераспределённый товар | Не заполнен хотя бы один из L1/L2/L3, статус или менеджер своего МП. В дерево групп не попадает, в «Итоги» входит, показывается в списке «требуют распределения». |
| `stock_ap` / `stock_daily` | Общий склад ТД АВТОПРОФИ из 1С (`stock_daily`, метрика «Остаток на складе АВТОПРОФИ»). Загрузчик — `app/ozon_stock_loader.py` (название историческое, склад общий). |
| Запас в днях | Оборачиваемость: остаток МП / среднедневные заказы за скользящие 30 дней. Пилюля в итоге последнего месяца у товара. |
| Частичный день | Текущий день, по которому есть только часть отчётов (отзывы, цены, склад). Показывается, но не меняет состав товаров и базу прогноза. |
| Статусы | CORE — основная боевая матрица; NEW — новинка или ещё не вышла на плановые показатели; Closeout — распродажа с целью вывода; Sale — плановая распродажа (промо, профицит); `?` — требует обсуждения; `-` — выведен/распродан, скрывается, если за период не было движений. Список и пояснения — `static/js/views.js` (STATUS_PRESETS, STATUS_LEGEND). |

## Общие правила

- **Масштаб процентов.** Все `*_pct` (СПП, CR, CTR, выкуп, отмены) в БД — доли 0..1; фронт умножает на 100.
  - WB «Рейтинг и отзывы»: ячейка с процентным форматом Excel уже доля; обычное число и текст с `%` делятся на 100.
    Масштаб берётся из формата ячейки, не из величины. `app/wb_reviews_loader.py:_to_spp`, `_read_sheet`. Тест: `tests/test_wb_reviews_percent.py`.
  - Прямые ценовые отчёты WB/Ozon: текст с `%` или число > 1 делятся на 100, число ≤ 1 считается долей; 0/пусто = нет СПП.
    `app/price_upload.py:_wb_spp`. Тест: `tests/test_wb_prices.py` (test_blank_first_sheet_and_real_percent).
  - WB «Воронка»: конверсии приходят процентами и делятся на 100; CTR рекламы = Σклики / Σпоказы (не сумма и не среднее готовых процентов). `app/wb_daily_loader.py`, `app/wb_ads_loader.py`. Тестов нет.
- **NULL ≠ 0.** Прочерк — нет данных, 0 — реальный ноль.
  - Дневные счётчики WB (заказы, отмены, переходы, корзины, CR) при существующей строке дня пустую ячейку пишут как 0 (`app/wb_daily_loader.py`, ZERO_FILL_COLS); снимки (рейтинг, позиция, остаток WB) остаются NULL.
  - Нет строки товара за день → в ячейке прочерк. Вчерашнее значение на пустой сегодняшний день не переносится. Тест: `tests/test_rnp_partial_days.py` (test_no_carry_from_yesterday, test_today_without_orders_keeps_values_and_dashes).
  - Суммы в РНП заказы: если в ячейку не пришло ни одного непустого значения — NULL, а не 0 (`rnp_sales_router.py:_cell_from_agg`).
- **Артикул.** Единственный ключ товара — артикул продавца после `app/util.py:canon_article`: обрезка и схлопывание пробелов, кириллические гомоглифы внутри латинского/цифрового контекста → латиница, верхний регистр. Применяется на всех точках записи. В запросах РНП заказы и ABC JOIN дополнительно защищён `UPPER()`; в юнит-экономике (`rnp_router.py:rnp_tree`) JOIN по точному совпадению. Тест: `tests/test_wb_prices.py` (test_canonical_article_and_header_alias), `tests/test_rnp_partial_days.py` (test_reviews_before_orders_upsert_canonical_and_repeat).
- **Перегруженные колонки** (ключи унифицированы под Ozon в `rnp_sales_router.py:_build_rnp_sales_tree`):
  - `delivery_time_hours` = «Количество отзывов» (WB/Яндекс: `reviews_qty` → этот ключ).
  - `stock_ozon_qty` = остаток своего МП: WB `stock_wb_qty`, Яндекс `stock_ya_qty`; подпись меняет `_metric_payload`.
  - `sku_ozon` у Яндекса = `ya_sku`, у WB = NULL.
- **Порядок групп** во всех деревьях (РНП заказы, юнит-экономика, продажи, цены, XLSX):
  - L1 — ECOM, затем ТД «АВТОПРОФИ» (поиск подстроки в верхнем регистре, устойчиво к кавычкам), затем прочие по алфавиту.
  - L2/L3 — алфавит без учёта регистра; товары — по артикулу.
  - Метрика и период порядок не меняют.
  - `app/util.py:l1_sort_key`, `cat_sort_key`. Тестов нет.
- **Признак «АВТОПРОФИ»** для формулы Pi — та же подстрока в L1 (`refresh_daily_pi`, `views.js:_idxIsAvtoprofi`, `price_export.py:index_workbook`). Переименование L1 без этой подстроки меняет формулу Pi.
- **Москва.** «Сегодня» для прогнозов и Pi — дата по МСК (UTC+3): `rnp_sales_router.py:_today`, `daily_pi.month_end`.
- **Кэш.** После записи загрузчик сбрасывает namespace своего МП (`cache.bump`); загрузка общего склада 1С сбрасывает деревья всех трёх МП. Без сброса сотрудники видят старые цифры до часа (TTL).

## Дневные загрузчики: что влияет на расчёт

Подробный реестр отчётов — `docs/data_sources.md`. Здесь только правила, от которых зависят цифры.

- **Перезапись диапазона дат.** Дневной файл заказов (Ozon, WB, Яндекс) удаляет строки своего диапазона дат и вставляет заново.
  - Поля других загрузчиков сохраняются по ключу дата + артикул (`PRESERVE_COLS`): реклама и CTR, отзывы и рейтинг, остаток АВТОПРОФИ, цены конкурентов, СПП и Pi WB.
  - Товар, пропавший из нового файла, сохраняет снимки (отзывы), но его заказы становятся NULL, а не старыми.
  - `app/ozon_daily_loader.py:load_ozon_daily`, `app/wb_daily_loader.py`. Тест: `tests/test_rnp_partial_days.py` (test_ozon_missing_from_orders_preserves_snapshot_not_orders, test_wb_preserves_spp_pi_reviews_for_matched_and_missing_articles).
- **Ozon, дневной файл** (лист «Данные»): заказы, суммы, отмены, Pi, СПП руб/%, переходы, CR, позиция, остаток Ozon. Проценты пишутся без пересчёта масштаба. Рейтинг из этого файла не берётся (колонка всегда пустая). Неизвестный артикул заводится в справочник и становится нераспределённым.
- **Ozon, «Список товаров»** → рейтинг и число отзывов (`delivery_time_hours`) по дате (`app/ozon_reviews_loader.py`). Реклама Ozon при отсутствии строки дня создаёт строку только с рекламой и CTR, заказы в ней NULL (не 0), чтобы расход не потерялся (`app/ozon_ads_loader.py`). ДРР из отчёта рекламы не берётся — считается в матрице.
- **WB, «Воронка»** создаёт дневную основу: заказы, отмены, переходы, корзины, конверсии, рейтинг, остаток WB, средняя позиция. Рейтинг WB берётся только отсюда.
- **WB, «Рейтинг и отзывы»** → `reviews_qty` и `spp_pct` по датам файла. Пустой СПП не стирает сохранённый. Для дат без строки «Воронки» создаётся заглушка только по товарам справочника (`app/wb_reviews_loader.py`). Тест: `tests/test_wb_reviews_percent.py`.
- **WB, «Индекс цен»** → `price_index_pi` = цена WB / цена идентичного товара; пустая или нулевая цена идентичного → NULL (`app/wb_pi_loader.py`).
- **PriceVA** (WB и Ozon): дата мониторинга выбирается в интерфейсе; артикулы сопоставляются без учёта регистра и лишних пробелов; для товаров без дневной строки создаётся заглушка (`app/wb_priceva_loader.py:load_wb_priceva`, `app/ozon_priceva_loader.py`).
- **Яндекс, «Аналитика продаж»**: показы, переходы, корзины, заказы, отмены. CTR = клики / показы, конверсии делятся на 100. СПП, Pi, реклама, позиция, отзывы, рейтинг и остаток Яндекса — заготовки без источника, показываются прочерком (`app/ya_daily_loader.py`).
- **Журнал.** Каждая загрузка, включая ошибку формата, пишется в `report_uploads` с видом отчёта (`period_kind`).

## Цены и Pi

- **Прямые дневные отчёты цен** (`app/price_upload.py:_parse_daily_report`, `app/price_history.py:sync_direct_report`):
  - Колонки ищутся по заголовку. WB «Цены с СПП»: Дата, Артикул продавца, Цена со скидки (загружаемая), Цена на витрине (с СПП), СПП, %; необязательно Время, Регион. Ozon: Дата, Артикул, Цена продавца после акций, ₽ (= загружаемая), Цена продавца с соинвестом, ₽, СПП/соинвест, %. Старые шаблоны («Цены и скидки», «Товары и цены») отклоняются.
  - Цена покупателя берётся из файла, не вычисляется. СПП 0 или пусто → СПП и цена покупателя NULL, загружаемая сохраняется (сигнал «товара нет в продаже»).
  - Ключ — дата + артикул + МП. WB: внутри дня берётся строка с самым поздним временем; одинаковое время с разными значениями или несколько регионов на ключ — ошибка. Ozon: разные значения одной даты/артикула — отказ всего файла.
  - Любая ошибочная строка отменяет весь импорт. Повторный файл перезаписывает только совпавшие ключи.
  - Тесты: `tests/test_wb_prices.py`, `tests/test_ozon_prices.py`.
- **РНП не перезаписывает прямые цены.** Пересчёт СПП/цены покупателя после загрузки РНП (`price_history.py:recalc_spp_and_buyer_from`) пропускает строки с источником `upload_wb_spp` / `upload_ozon_coinvest`, включая строки с NULL-СПП. Тесты: test_rnp_cannot_replace_direct_wb_prices_or_missing_stock (`tests/test_wb_prices.py`), test_rnp_cannot_change_direct_or_no_stock_and_wb_is_untouched (`tests/test_ozon_prices.py`).
- **Старые строки `mp_price_daily`** (другие источники): СПП — точная за тот же день из `*_daily_sales`, иначе последняя известная раньше (помечается `spp_is_estimated`, в интерфейсе «≈»), иначе NULL. `price_history.py:recalc_spp_and_buyer_from`, `resolve_spp_for`, `sync_uploaded_prices`. Тест: test_legacy_wb_and_ozon_recalc_remain_unchanged.
- **Базовые цены** (`prices_router.py:price_cell`, `prices_import`, `_append_base_price_history`):
  - Ручная правка — любой авторизованный (двойной клик); импорт Excel — только admin.
  - Шаблон: «Артикул», «Базовая OZON», «Базовая WB», «Базовая Yandex»; столбцы ищутся по шапке. Пустая ячейка = удалить цену, неизвестный артикул пропускается.
  - При изменении закрывается активный интервал истории и открывается новый; то же значение историю не пополняет.
  - Состав шаблона = то, что видно в прайс-листе за период.
- **Дневные Pi** (`migrations/2026_09_21_daily_pi.sql`: `refresh_daily_pi`, триггеры на `mp_price_daily`, `catalog_base_prices_hist`, `catalog_items`; чтение — `app/daily_pi.py:load`):
  - Строятся только для дат, реально присутствующих в `mp_price_daily` (Ozon/WB); дни не выдумываются.
  - Цена покупателя годится для Pi, только если СПП > 0, не оценочная, СПП взята за эту же дату и цена > 0.
  - Базовая цена — та, что действовала на конец московских суток этой даты.
  - `wb_base_pi`/`ozon_base_pi` = (L1 с «АВТОПРОФИ» ? покупатель : загружаемая) / базовая; при базовой ≤ 0 или NULL — NULL.
  - `buyer_pi` = покупатель Ozon / покупатель WB; NULL, если любой из них непригоден.
  - Смена цены, базовой цены или категории пересчитывает затронутые артикулы/даты в той же транзакции.
  - Тест: `tests/test_daily_pi.py` (no_carry_between_dates, zero_spp_and_estimated_legacy_not_used, autoprofi_and_category_change, base_history_correction_and_moscow_midnight, atomic_rollback, concurrent_imports_converge).
- **Pi в РНП заказы** (только Ozon и WB, только строка товара): «Индекс цены, Pi» раскрывается в «Базовая цена, Pi» и «Цена покупателя Ozon / WB, Pi».
  - День — точное значение этой даты, иначе прочерк.
  - Итог месяца — срез на `daily_pi.month_end`: прошедший месяц → календарный конец (или конец выбранного периода, если раньше); текущий → последний показанный день ≤ сегодня. Средние по дням не считаются.
  - Сам «Индекс цены, Pi» кабинета в итоге месяца — среднее дневных значений > 0 (он в AVG_COLS), это не срез.
  - `rnp_sales_router.py:_build_rnp_sales_tree.finalize`. Тест: `tests/test_daily_pi.py` (month_end_rules, past_month_uses_calendar_end_even_without_orders_that_day, same_buyer_in_both_rnp_and_existing_pi_unchanged, cached_rnp_invalidates_for_either_source).
- **Раздел «Цены → Индекс цен»** (`prices_router.py:pricelist` + `static/js/views.js:_idxWbPi`, `_idxOzPi`, `_idxBuyerPi`):
  - В отличие от РНП, берётся последний известный срез `mp_price_daily` на дату ≤ конца периода (перенос допустим).
  - Базовая — последняя запись истории с `valid_from` ≤ конец периода + 1 день; себестоимость — срез `item_cost_hist` на конец периода.
  - Pi считается на фронте по тем же формулам, но цена покупателя АВТОПРОФИ используется и при оценочной СПП.
  - Состав при заданном периоде — только артикулы с движением в `fact_weekly` Ozon/WB за пересекающиеся недели. Товары только Яндекса не попадают.
- **Пороги раскраски Pi** (сравнивается значение, округлённое до 2 знаков):

| Pi | Красный | Чёрный | Синий | Где |
|---|---|---|---|---|
| Pi к базовой, прочие группы | < 1,00 | 1,00–1,10 | > 1,10 | `views.js:_idxPi`, XLSX `price_export.py:index_workbook` |
| Pi к базовой, L1 «АВТОПРОФИ» | < 1,15 | ≥ 1,15 | — | `views.js:_idxPiAvtoprofi`, XLSX то же |
| Pi покупатель Ozon / WB | < 1,03 | ≥ 1,03 | — | `views.js:_idxPiPlain`, XLSX то же |

- **XLSX «Индекс цен»** (`app/price_export.py:index_workbook`, `prices_router.py:prices_index_export`; тест: `tests/test_price_export.py`):
  - Имя файла и заголовок — «Индекс цен на маркетплейсах ДД.ММ.ГГГГ», дата по МСК.
  - Учитывает период и поиск; те же данные и формулы, что на экране.
  - Колонка себестоимости — только при включённом флажке «Показать себестоимость» (то же для выгрузки прайс-листа).
  - Комментариев с датами актуальности цены/себестоимости нет; у оценочной СПП — маркер «≈» и короткое примечание.
  - В ячейках Pi — формулы Excel плюс сохранённые значения; нет данных — «–».

## РНП заказы (дневной отчёт)

Код: `app/routers/rnp_sales_router.py:_build_rnp_sales_tree`. Источники: `ozon_daily_sales`, `wb_daily_sales`, `ya_daily_sales` + `catalog_items` (L1–L3) + `catalog_marketplace` (статус/менеджер своего МП) + `stock_daily` + `sales_plan`.

- **Дерево**: Итоги → L1 → L2 → L3 → товар. Колонки — месяцы с данными; у месяца блок дней (раскрывается), итог, план, прогноз.
- **Наборы метрик** (`GROUP_METRIC_DEFS`, `PRODUCT_METRIC_DEFS`, `_metric_payload`):
  - Верхняя строка любого узла — «Заказы, шт».
  - Группа и «Итоги»: сумма заказов, ДРР, реклама, процент отмен, CTR, CR корзина, CR заказ. Pi, отзывы, рейтинг, остатки у групп не выводятся.
  - Товар: 20 метрик + подгруппа «Цены» (ср. загружаемая → цена для покупателя, конкуренты средняя/минимальная) + раскрытие Pi (кроме Яндекса).
  - Яндекс: добавлены «Показы, общие»; CTR подписан «CTR, общий».

- **Агрегация день → месяц → группы** (`Agg`, `_cell_from_agg`):
  - Сумма: заказы шт/руб, отмены, переходы, показы (только Яндекс), реклама руб, СПП руб.
  - Среднее по значениям > 0: CR корзина/заказ, CTR, средняя позиция, Pi кабинета, СПП, цены конкурентов. Средневзвешенные без согласования не вводить.
  - Снимки в дневной ячейке группы — сумма значений товаров за день; в итоге месяца — по правилам ниже.
- **Расчётные метрики ячейки:**
  - Процент отмен = отмены / заказы (если заказы > 0).
  - ДРР общая = реклама / сумма заказов (если сумма > 0).
  - Ср. загружаемая цена = сумма заказов / заказы шт.
  - Цена для покупателя = ср. загружаемая × (1 − СПП ячейки).
  - На Ozon-строках `avg_upload_price`/`price_for_buyer` из файла перекрываются этим расчётом.
- **Месячные снимки** (`month_snapshot`):
  - Рейтинг и отзывы — последнее непустое значение товара в месяце.
  - Остатки (МП и АВТОПРОФИ) — строго на последнюю дату строки товара в месяце; NULL остаётся прочерком, старый остаток не подтягивается.
  - Группа = сумма снимков товаров.
- **Запас в днях** (`node_turnover`, считается только для последнего месяца данных):
  - Окно — 30 дней до опорной даты. Опорная дата — последняя дата с фактом заказов (для Яндекса — любая дата), не позже сегодня.
  - Знаменатель — число дней окна с данными (не календарные дни).
  - Остаток: Ozon/Яндекс — месячный снимок остатка МП; WB — остаток строго на опорную дату (день только с отзывами/СПП базу не сдвигает).
  - Результат: остаток NULL → NULL; остаток ≤ 0 → 0; есть остаток, нет заказов → `inf` (∞); иначе остаток / (заказы окна / дни окна).
  - Тест: `tests/test_rnp_partial_days.py` (test_wb_reviews_only_day_keeps_turnover_but_not_daily_stock, test_wb_turnover_*, test_snapshot_day_does_not_reduce_forecast_or_raise_turnover).
- **Светофор запаса** (`views.js:rnpsTurnBadge`): только товар, итог последнего месяца; < порога 1 — красный (недостаточно), > порога 2 или ∞ — синий (излишек), между — зелёный. Пороги и вкл/выкл — строка `turnover_days` в `anomaly_rules` (по умолчанию в коде 20/60). Значение округляется до целого.
- **План и прогноз** (`node_plan`, `node_forecast`):
  - План месяца — сумма `sales_plan` по артикулам узла.
  - Прошедший месяц: прогноз = факт / план.
  - Текущий: факт / дни с фактом заказов × дней в месяце / план. День, где есть только отзывы/цены/склад, не считается; реальный 0 заказов — считается. Яндекс считает все дни с данными.
  - Будущий месяц или нет плана → NULL.
  - Светофор: ≥ 100% зелёный, 70–99% жёлтый, < 70% красный (`views.js:rnpsFcClass`).
  - Тест: `tests/test_rnp_partial_days.py` (test_actual_zero_is_a_day_with_orders_data, test_snapshot_only_has_no_forecast).
- **Тепловая шкала «Заказы, шт»** (`views.js:rnpsNodeHeatRange`, `rnpsHeatColor`): только дневные ячейки товаров; мин/макс — по видимым дням этой строки. Итоги, план, прогноз, группы в шкалу не входят.
- **Частичные дни и общий склад:**
  - Состав товаров задают только дневные строки РНП выбранного периода.
  - `stock_daily` (Ozon, WB) дополняет даты и остаток АВТОПРОФИ только у уже попавших артикулов. Новых товаров, итогов или записей в списке нераспределённых не создаёт.
  - Яндекс: общий склад только присоединяется к существующим строкам, отдельного дополнения нет.
  - Тест: `tests/test_rnp_partial_days.py` (test_stock_updates_existing_day_without_adding_stock_only_article, test_stock_only_unallocated_article_does_not_affect_warning_or_totals, test_stock_without_daily_source_keeps_report_empty, test_yandex_does_not_join_common_stock_or_change_forecast).
- **Состав и исключения** (основной цикл `_build_rnp_sales_tree`):
  - Активность за период: заказы шт/руб, реклама или остаток МП > 0. Остаток АВТОПРОФИ, отзывы, цены активностью не считаются.
  - Статус `-` без активности скрывается; явный фильтр по `-` показывает все такие товары. `?` и прочие статусы не скрываются. Тест: test_common_stock_does_not_activate_inactive_dash_status.
  - Только WB (05.10.2026): пустой/NULL/пробельный статус без активности — товар не попадает ни в РНП, ни в список нераспределённых; при появлении активности возвращается с обычной проверкой. Ozon и Яндекс не затронуты. Тест: test_wb_blank_status_*, test_wb_whitespace_status_with_activity_is_unassigned, test_blank_status_rule_does_not_change_other_marketplaces.
  - Нераспределённый: пустой L1/L2/L3, статус или менеджер (у WB статус проверяется после обрезки пробелов). Входит в «Итоги», в группы — нет.
- **Красная монетка у товара**: маржинальность последней недели `fact_weekly` < 0, тот же расчёт, что в юнит-экономике (`rnp_router.py:negative_margin_articles`). Окно «экономика товара» — 6 метрик за 3 последние недели (`rnp_router.py:rnp_product_ue`).
- **Кэш**: ключ по нормализованному МП (`wb` = `wildberries`), дате МСК, ревизии Pi, периоду и фильтрам; отдельные namespace Ozon/WB/Яндекс. Любая правка справочника сбрасывает все три (`catalog_router.py:_invalidate_rnp_trees`). Тест: `tests/test_catalog_status_cache.py`.

## Юнит-экономика (недельная)

Код: `app/routers/rnp_router.py:rnp_tree`, `_compute_cell`, `_add_row`; сводная — `rnp_tree_cross`, `_collect_mp_raw`. Источник — `fact_weekly` (`row_type='Товар'`). Тестов нет.

- **Агрегация**: рублёвые и штучные колонки суммируются по товарам узла. Доли = сумма руб / выручка, удельные = сумма руб / шт. Выкуп и СПП — Σ(доля × выручка) / Σвыручки. При нулевой выручке доли = NULL.
- **Прибыль WB** = Σ`wb_profit_with_ads` («Прибыль (с рекл.)» из отчёта). В корень дополнительно прибавляется `wb_profit_with_ads` строк «Общие удержания». Реклама и `noart_exp` повторно не вычитаются.
- **Прибыль Ozon** (и Яндекс — та же ветка) = Σ`profit` − `noart_exp`, где `noart_exp` = Σ`holds_total` строк «Общие удержания». Вычитается только в корне «Итоги»; у групп и товаров `noart_exp` = NULL.
- **Знаки**: Ozon `promo_total` хранится отрицательным → расход продвижения = −`promo_total`. WB: реклама в `wb_ads_total` (положительная), `promo_total` = 0.
- **Метрики карточки товара/группы** (`PRODUCT_METRIC_DEFS`):
  - «Продвижение, от продаж» = расход продвижения / выручка; «от заказов» = расход / заказы руб.
  - «Все удержания» = комиссия + эквайринг + логистика + хранение (+ утилизация Ozon) + штрафы. Продвижение и себестоимость не входят.
  - Заказы руб — готовая колонка, если она > 0, иначе заказы шт × (выручка / продажи шт).
- **Устаревшие ключи**: `drr_pct` и `promo_pct` = `promo_total` / выручка (Ozon — со знаком минус, WB — 0), `ads_diff_pct` = −`promo_pct`. Не ориентироваться на подпись.
- **Дельта к прошлой неделе** красится по полярности: `neg` (расходы) — рост красный, `pos` — рост зелёный, план без дельты (`views.js:deltaDirPolar`).
- **Светофор маржинальности** (`views.js:marginSignalClass`): < 0 — красный (галочка, включена по умолчанию); 0 ≤ маржа < целевой — оранжевый, если пользователь ввёл целевую %.
- **Состав**:
  - Статус `-` скрывается, если ни в одной загруженной неделе нет движения (выручка, продажи, заказы, возвраты, прибыль или удержания ≠ 0).
  - Нераспределённые — в «Итоги», не в группы.
  - Полностью распределённая карточка справочника без факта получает пустую строку на последнюю неделю, чтобы новинка была видна сразу.
- **План по неделям** (`_plan_by_node_week`): дневная доля = месячный план / дней в месяце; неделя = сумма долей своих дней `period_start..period_end`, недели на стыке месяцев берут доли обоих. План нераспределённых артикулов — только в корне. Вывод с 1 знаком.
- **Сводная** (`rnp_tree_cross`, `cross_cell`):
  - Рубли и штуки Ozon и WB складываются; прибыль каждого МП уже посчитана по своим правилам.
  - Маржинальность и «Все удержания, %» пересчитываются от общей выручки; готовые проценты не суммируются.
  - План — по обоим МП; у товара показываются оба статуса (Ozon и WB) отдельно.
- **Групповые метрики** (`views.js`, GROUP_ONLY_PLAN): доля в общей выручке, возвраты %, число убыточных SKU, доля A-товаров; «Прочие удержания (общие), руб» — только в «Итогах».
- **Неделя в фильтре периода** видна, если хотя бы один её день попадает в выбранный диапазон (`views.js`, rnpVisibleWeeks).
- **«Доля A-товаров» у групп** берёт `abc_revenue` из `fact_weekly` (класс из файла MPPROFIT), а не клиентский ABC.

## Продажи, шт. и план

Код: `app/routers/sales_router.py:_compute_plan_fact`, `plan_cell`, `plan_import`, `report_export`. Тестов нет.

- Факт — `fact_monthly` (`row_type='Товар'`), план — `sales_plan` (артикул, МП, год, месяц). Группы суммируют товары; сводная — Ozon + WB + Яндекс.
- **Прогноз месяца**:
  - База — `report_uploads.fact_through_date` последнего месячного отчёта за месяц (по МП), а не дни с данными, как в РНП заказы.
  - Если день этой даты < дней в месяце → факт / день × дней месяца, флаг partial; иначе (даты нет или месяц полный) прогноз = факт.
  - Для сводной прогноз считается по каждому МП и суммируется.
- **YoY**: факт прошлого года показывается только для артикулов, которые есть в текущем году.
- **Светофор** (`views.js:spPctClass`, `spFcClass`): ≥ 100% зелёный, 70–99% жёлтый, < 70% красный.
- **План в рублях**: закрытый месяц (у загрузки `fact_monthly` `fact_through_date` IS NULL) — по средней цене месяца из факта; незакрытый/будущий — по последней недельной `avg_sale_price` с продажами.
- **Состав**: артикулы с фактом или планом года + полностью распределённые карточки справочника. Нераспределённые не исключаются, а идут в группы «(без категории)». Пустой статус для фильтра = `-`.
- **Ручная правка плана** (`plan_cell`) ставит `is_manual`; `prev_qty` не трогает — там значение из последнего Excel-импорта. Показывается только на листе одиночного МП.
- **Импорт плана** (`plan_import`): UPSERT по артикул + МП + год + месяц; пустая ячейка месяца удаляет план.
- **XLSX «Продажи, шт»** (`report_export`): иерархия с группировкой строк, светофор прогноза теми же порогами.

## ABC

Код: `static/js/abc_module.js:computeAll`, `aggregate`, `abcClassify`, `makeRecommendation`, `isDashNoMove`; данные — `app/routers/abc_router.py:abc_data`. Тестов нет.

- Считается в браузере по `fact_monthly`. Колонки `abc_*` из MPPROFIT не используются (`abc_profit` там испорчен).
- **Период** → набор месяцев, пересекающих выбранный диапазон; ключ месяца — год+месяц.
- **Классы**: сортировка по убыванию значения; доля = накопленная сумма с текущим SKU / сумма положительных. A ≤ 80%, B ≤ 95%, C — остальное; отрицательное → D, ноль → Z. Выручка и прибыль классифицируются отдельно, комбинированный код = класс выручки + класс прибыли.
- **Прибыль**: WB — `wb_profit_with_ads`, Ozon и Яндекс — `profit`. Общие удержания отдаются отдельным массивом и в классификацию не входят.
- **Яндекс** классифицируется самостоятельно и в матрицу «Сравнение МП» (Ozon ↔ WB) не входит.
- **Рекомендации** (`makeRecommendation`, проверяются по порядку):
  - AA → KEEP_STAR; класс выручки Z (нет продаж) → REMOVE.
  - Убыток: если на другом МП прибыль и класс выручки A/B → REMOVE_HERE, иначе REMOVE.
  - Здесь B/C, на другом МП A и прибыль там ≥ 5× → REMOVE_HERE при выручке здесь < 100 000 ₽.
  - Здесь C, на другом A/B и прибыль ≥ 3× → CONSIDER_REMOVE_HERE.
  - CC: выручка < 30 000 ₽ → REMOVE, иначе REVIEW. Маржа < 5% и прибыль < 30 000 ₽ (не A) → REVIEW. Остальное → KEEP.
  - Прогноз матрицы «после плана действий» снимает товар с МП при кодах REMOVE, REMOVE_HERE, CONSIDER_REMOVE_HERE.
- **ДРР в ABC** = рекламный расход / выручка: Ozon и Яндекс — `promo_total`, WB — `wb_ads_total`.
- Статус `-` без движения (выручка, продажи, заказы, возвраты, прибыль = 0) скрывается; в сравнении товар исчезает, только если скрыт на обоих МП.

## Склады

Код: `app/routers/warehouses_router.py:by_wh`, `data_quality`, `incident_*`; `app/routers/ozon_warehouses_router.py` (то же для Ozon); рендер — `static/js/views.js:whRenderByWh` и блок «Склады Ozon». Тестов нет.

- **Три контура остатков — не смешивать:**
  1. Остаток МП в РНП: `ozon_daily_sales.stock_ozon_qty`, `wb_daily_sales.stock_wb_qty`, `ya_daily_sales.stock_ya_qty`.
  2. Общий склад 1С: `stock_daily` → «Остаток на складе АВТОПРОФИ». Загрузка перезаписывает день и копирует значение в `ozon_daily_sales.stock_ap_qty` у существующих строк, новых строк продаж не создаёт (`app/ozon_stock_loader.py`).
  3. Стоимостные остатки по складам: `wb_stock_daily`, `ozon_stock_daily` (раздел «Склады»).
- **Загрузка по складам**: колонки правее «Всего находится на складах» — склады (длинная модель дата × артикул × склад). Повторная загрузка заменяет только этот день. Новые склады и новые артикулы заводятся автоматически; новый артикул попадает в нераспределённые.
- **Оценка** (переключатель «себестоимость / цены продажи»):
  - Себестоимость — срез `item_cost_hist` на дату остатка (последняя запись с `start_date` ≤ даты и `cost_calc` > 0); общая для WB и Ozon. Загружается отдельным справочником (`app/cost_loader.py`).
  - Цена продажи — `fact_monthly.avg_sale_price` своего МП (у Ozon своя цена), последняя по месяцу, применяется ко всем датам.
  - Без цены или себестоимости товар даёт 0 и попадает в баннер достоверности (`data_quality`).
- **Сортировка складов** — по стоимости в ценах продажи на последнюю дату, по убыванию.
- **Иерархия**: WB — округ → склад; Ozon — округ → кластер → склад. Без округа — «Не распределённые». Синонимы склеиваются через `canonical_id`.
- **Инциденты** — интервалы на каноничном складе:
  - Один открытый интервал на склад: открытие более ранней датой расширяет его влево, более поздней — игнорируется.
  - «Закрыть с даты D» → последний день = D − 1; если это раньше начала — интервал удаляется.
- **KPI «из них — инцидент»**: остатки складов с активным инцидентом на последнюю дату, отдельно себестоимость и цены продажи; счётчик — число складов.
- **Пропавший склад**: остаток на предпоследней дате > 0, на последней — 0.
- **Заморозка (только Ozon, только на фронте, БД не меняется)**: внутри активного инцидента, если реальное значение пусто/0, показывается последнее более раннее ненулевое значение. На него опираются ячейка, KPI, подытоги, спарклайн. Вне инцидента ноль не переносится. WB не замораживает.
- Подраздел «Общие данные» отложен — заглушку не считать реализацией.

## Товары и статусы

- Категории L1–L3 и наименование общие (`catalog_items`); статус, менеджер и ссылка — по МП (`catalog_marketplace`, ключ артикул + МП).
- Смена статуса из «Товаров», РНП заказы или юнит-экономики пишет одну запись выбранного МП; другие МП не меняются. Нельзя обещать «один статус на всех площадках». `app/routers/catalog_router.py:update_item`, `import_items`. Тест: `tests/test_catalog_status_cache.py`.
- Сохранение создаёт строку `catalog_marketplace` даже без статуса — так товар «заведён» на МП. Любая правка или импорт сбрасывает кэши деревьев РНП всех трёх МП.
- Правило скрытия `-` в каждом разделе своё: РНП заказы — заказы/реклама/остаток МП; юнит-экономика и ABC — выручка/продажи/заказы/возвраты/прибыль(/удержания); прайс-лист — только артикулы с движением в `fact_weekly`.

## Аномалии (как реально работает)

Код: `app/routers/rnp_anomalies_router.py:anomalies`, `_resolve_periods`, `_period_metrics`, `_snapshot_latest`, `_rel_values`, `_forecast_by_art`; фронт — `static/js/views.js:rnpsLoadAnomalies`. Тестов нет.

- **Источник — только `ozon_daily_sales`.**
  - SQL читает таблицу Ozon при любом `marketplace`; фронт всегда шлёт `marketplace=ozon`.
  - Кнопка «Аномалии» есть в общей панели РНП и на вкладках WB/Яндекс, но там фильтрует товары по срабатываниям, посчитанным на данных Ozon (совпадение по артикулу).
  - Параметр `marketplace` влияет только на план в правиле прогноза.
  - Уровень — только товар; группы служат контейнерами.
- **Правила** читаются из таблицы `anomaly_rules` в БД (порог, второй порог, вкл/выкл; правятся шестерёнкой). Снимок значений в документацию не копировать — смотреть в БД.
- **Периоды**: `rolling7` — последние 7 дней до последней даты данных и 7 дней перед ними; `week` — ISO-неделя с последней датой и предыдущая; `custom` — заданный интервал и такой же длины перед ним.
- **rel** (динамика): изменение = (тек − пред) / |пред| × 100.
  - Заказы, отмены, переходы — сумма за период / календарные дни периода.
  - CR, CTR, позиция, СПП — среднее значений > 0.
  - ДРР — реклама / сумма заказов за период.
  - Направления: `down`, `up`, `both`, `dev`. Нет предыдущего периода или пред = 0 → не применяется.
- **abs**: рейтинг, отзывы, Pi кабинета — значение в последней строке товара внутри текущего периода; NULL → правило пропускается.
- **cover**: остаток (Ozon или копия АВТОПРОФИ в `ozon_daily_sales.stock_ap_qty`) / среднедневные заказы за 7 дней до конца текущего периода. Нет продаж: срабатывает только при остатке ≤ 0.
- **forecast**: последний месяц данных; текущий месяц — дни с любыми данными (а не только с заказами, в отличие от дерева); срабатывает при прогнозе < порога 1 или > порога 2 (в %).
- **filter `no_ads`**: нет расходов на рекламу в текущем периоде. Флаг `ads_only` у правила — товары без рекламы пропускаются.
- **`turnover_days`** в фильтре не участвует (ANOM_NONFILTER_KINDS): его пороги только красят пилюлю запаса в дереве.
- Фильтр применяется только по кнопке «Применить»; товар проходит, если сработало хотя бы одно выбранное правило.

## Известные расхождения и риски (на 07.10.2026)

Расхождения выгрузки Perplexity с кодом и места, где код противоречит сам себе. Ничего из этого
не исправлено; без согласования с владельцем не трогать.

- Аномалии: в выгрузке «только WB/Ozon, не Яндекс». По коду — только Ozon (см. раздел выше).
- Аномалии, `cover`: в выгрузке «за используемый период». По коду — всегда 7 календарных дней до конца текущего периода.
- Аномалии, `forecast`: база — дни с любыми данными, а в дереве РНП — только дни с фактом заказов. Прогнозы могут не совпасть.
- Юнит-экономика: подпись `drr_pct` «ДРР % к заказам», а знаменатель по коду — выручка (знак Ozon отрицательный).
- ABC: комментарий в `abc_router.py` обещает, что клиент берёт `promo_total` по модулю, но `abc_module.js` знак не снимает. При отрицательном `promo_total` ДРР Ozon/Яндекс в ABC будет отрицательной — сверить на данных.
- ABC: в памяти Perplexity классификация описана для Ozon/WB. В коде есть и Яндекс (отдельно, без участия в сравнении МП).
- Склады: цена продажи берётся из `fact_monthly` с сортировкой только по месяцу, без года. На стыке лет «последний месяц» может оказаться прошлогодним (`PRICE_CTE` в обоих роутерах складов).
- Склады, заморозка Ozon: в памяти — «значение до начала интервала». По коду — последнее ненулевое до текущей даты, включая дни внутри интервала.
- Цены: в памяти загружаемая цена WB = текущая цена × (1 − скидка продавца). По коду старый шаблон отклоняется, загружаемая берётся из колонки «Цена со скидки (загружаемая)».
- Цены: дневной Pi не использует оценочную СПП, а «Цены → Индекс цен» для АВТОПРОФИ берёт цену покупателя и при оценочной СПП. Значения Pi в РНП и в «Ценах» могут расходиться.
- Прямые отчёты цен угадывают масштаб СПП по величине (> 1 → проценты), что противоречит общему правилу «не угадывать масштаб». Для СПП ≤ 1% в процентных пунктах это ошибка.
- `views.js:_idxBuyerPi`: комментарий «раскраска не применяется», а `_idxPiPlain` красит < 1,03.
- Прайс-лист: docstring `pricelist` говорит «статус `-` без движения скрыть», а SQL показывает только артикулы с движением независимо от статуса.
- Юнит-экономика: «Доля A-товаров» опирается на `abc_revenue` из файла MPPROFIT, тогда как раздел ABC эти колонки игнорирует.
- Юнит-экономика: подпись «служебные удержания — серым» в комментарии `PRODUCT_METRIC_DEFS`, а цвет по коду почти чёрный `16191D`.
