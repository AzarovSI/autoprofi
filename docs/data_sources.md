# Реестр загружаемых отчётов

Обновлено: 07.10.2026. Сверено с кодом: `app/routers/upload_router.py`, `prices_router.py`,
`catalog_router.py`, `sales_router.py`, `app/*_loader.py`, `app/loader_core.py`,
`app/price_upload.py`, `app/price_history.py`. Пути в кабинетах взяты из подсказок интерфейса
(`static/js/views.js`) и выгрузки Perplexity, входом в кабинеты не проверялись.

Все данные приходят файлами вручную. API-интеграций с площадками нет.
Кто фактически загружает каждый отчёт и по какому графику: НЕ ЗНАЮ. Колонка «Право» показывает
серверную проверку: **admin** — `auth.require_admin`, **авториз.** — любой вошедший (`auth.get_current_user`).
Таблица `report_uploads` (журнал) в колонке «Таблицы» не повторяется: в неё пишут все загрузчики
из `upload_router.py`.

## 1. MPPROFIT: юнит-экономика, продажи, ABC

Один загрузчик на 6 вариантов (WB / Ozon / Яндекс × неделя / месяц): `loader_core.py:load_report`,
`POST /api/upload/report` (поля `marketplace`, `file`, необязательное `fact_through_date`), право **admin**.

| Параметр | Значение |
|---|---|
| Откуда | Сервис MPPROFIT, Excel-отчёт за период. Путь кнопок НЕ ЗНАЮ |
| Файл / лист | Имя произвольное; читается **активный лист** (openpyxl) |
| Где дата | Строка 2, ячейка A–E с текстом «Период … ГГГГ-ММ-ДД - ГГГГ-ММ-ДД» |
| Раскладка | Шапка — строки 4–5, ИТОГО — строка 6, товары — с 7-й |
| Тип периода | `detect_period_kind`: (конец − начало) 5–7 дн. → неделя, 27–31 дн. → месяц, иначе отказ |
| Таблицы | Неделя → `fact_weekly`, месяц → `fact_monthly`; новые артикулы → `catalog_items`, `catalog_marketplace` |
| Режим | **Заменяет период**: `DELETE` по (год, неделя/месяц, МП) + `INSERT` батчами по 100 |
| Ключ периода | Неделя — ISO-неделя и ISO-год даты начала; месяц — месяц и календарный год даты начала |
| Где используется | `fact_weekly` — РНП юнит-экономика, метрики, тренды; `fact_monthly` — «Продажи, шт.», ABC |

Ловушки:
- **Неполный месяц.** Отчёт с периодом короче 28 дней не будет месячным: 01–07 число распознается
  как неделя. Неполный месяц грузится с периодом на весь месяц и полем «Факт по дату»
  (`report_uploads.fact_through_date`, влияет на прогноз в «Продажи, шт.»).
- **Смена формата Ozon (июнь 2026).** Старые и новые названия колонок сведены в `OZ_NAME_ALIASES`.
  Проверка формата идёт по наличию ключевых заголовков (`OZ_REQUIRED`, `WB_REQUIRED`), а не по позициям.
- **Яндекс:** двухуровневая шапка, колонки ищутся по составному ключу «Секция :: Метрика»
  (`build_ya_colidx`, секции протягиваются через объединённые ячейки). `promo_total` записывается
  с минусом, как у Ozon.
- **Общие удержания** (Ozon и Яндекс): строка «Общие удержания» получает только нераспределённый
  остаток = «Все удержания» из ИТОГО − Σ удержаний по товарам. У Яндекса такую строку загрузчик
  создаёт сам, если её нет в файле.
- **Проценты** берутся как значение ячейки: знак «%» отбрасывается, на 100 не делится.
  Масштаб зависит от формата ячейки в файле MPPROFIT.
- Дубли товара (артикул + штрихкод WB / SKU Ozon в одном периоде) отклоняют всю загрузку.
  Строки без артикула и без штрихкода/SKU пропускаются.
- Категории L1–L3 и статус копируются в строки факта из `catalog_items` **на момент загрузки**.
- Новые артикулы попадают в справочник отдельным commit до записи факта и остаются там, даже если
  загрузка потом упала.
- Кэш после загрузки не сбрасывается: разделы на `fact_*` кэш не используют.

Ловушки и особенности:

- **R1 Ozon дневной.** Удаляются **все** строки за диапазон дат файла. Поля других загрузчиков
  (`rating`, `delivery_time_hours`, `ads_expense_rub`, `ctr_pct`, `stock_ap_qty`, `avg_upload_price`,
  `price_for_buyer`, `comp_price_*`, `drr_total_pct`) сохраняются (`PRESERVE_COLS`). Если артикула
  нет в новом файле, его строка остаётся заглушкой только с этими полями. Неполный по товарам файл
  стирает заказы остальных товаров. «Рейтинг (отзывы)» из файла не берётся. Проценты (`spp_pct`,
  `cr_*`) записываются как в файле, без деления на 100. После загрузки выполняется
  `price_history.recalc_spp_and_buyer_from("Ozon", min_date)`.
- **R2 Ozon реклама.** Расход по SKU суммируется, CTR = Σ кликов / Σ показов (доля). Если в файле
  период из нескольких дней, вся сумма расхода запишется **в каждый день** диапазона. Грузить
  строго по одному дню. Неизвестные SKU (без истории продаж) идут в unmatched. Обновление идёт
  построчными `UPDATE`.
- **`SharedStrings.xml` с заглавной S** встречается в выгрузках WB, Ozon и 1С, openpyxl на нём
  падает. R3, R4, R8, R9 и S1 при ошибке пересобирают zip для openpyxl. R5, R7, R10, S2, S3 и S4
  читают через `python_calamine`, R11 пробует calamine первым.
- **R5 WB Воронка.** openpyxl падает на `SharedStrings.xml`, поэтому файл читается через
  `python_calamine`. CR приходят процентными пунктами и делятся на 100. Пустые счётчики при
  существующей строке пишутся как 0 (`ZERO_FILL_COLS`); снимки (`rating`, `stock_wb_qty`)
  остаются NULL. `PRESERVE_COLS`: `reviews_qty`, `ads_*`, `ctr_pct`, `stock_ap_qty`, `comp_price_*`,
  `price_index_pi`, `spp_pct`. После загрузки выполняется
  `recalc_spp_and_buyer_from("Wildberries", min_date)`.
- **R6 WB СПП.** Масштаб берётся из формата ячейки: Excel-процент — доля, число или текст
  с «%» — процентные пункты (исправлено 07.10.2026). Значение вне 0–100 % — ошибка. Пустая СПП
  не затирает сохранённую. СПП пишется только в существующие строки, заглушки создаются только
  для отзывов (товары из справочника). «РейтингТовара» не берётся, рейтинг приходит из R5.
  XLSX читается через openpyxl, чтобы видеть формат ячеек. Если файл придёт с `SharedStrings.xml`,
  возможна ошибка чтения (как у R5) — не проверено.
- **R7 WB реклама.** CTR = Σ clicks / Σ views, CPC = Σ затрат / Σ clicks. Заглушки создаются
  только для товаров из справочника.
- **R4/R8 PriceVA.** Формат файла общий, данные разные. Колонки «Мин./Средняя цена» в объединённых
  ячейках ищутся по имени. Обе загрузки пишут `period_kind='competitors'`, поэтому WB PriceVA
  попадает в журнал «РНП Ozon» (`kind=rnps_ozon`) и не попадает в `rnps_wb`.
- **R9 WB Pi.** Pi = «Цена товара на WB» / «Цена идентичного товара» (пусто или 0 → NULL).
  Два файла одной даты грузятся по очереди, второй не стирает первый. Это Pi кабинета, а не прямой
  ценовой импорт раздела «Цены».
- **R10 Яндекс.** CR делятся на 100, CTR = клики / показы. Строки, которых нет в новом файле,
  удаляются **вместе** с сохраняемыми полями, включая `stock_ya_qty` у заготовок R11. После
  повторной загрузки R10 за дату перезагрузить R11 за ту же дату.
- **R11 Яндекс остатки.** «Доступно для заказа» суммируется по артикулу (строка «Склад: все»
  плюс строки складов). Агрегацию не менять без исходного файла.
- **S1 общий склад.** Остаток записывается только по товарам из справочника и **не добавляет**
  товаров в РНП. В Ozon остаток синхронизируется в `stock_ap_qty`, WB и Яндекс берут его через
  JOIN с `stock_daily`. Сбрасывается кэш всех трёх деревьев.
- **S2/S3 склады.** Неизвестные товары и склады создаются автоматически (старый docstring WB про
  «только известные товары» устарел). S3 берёт колонки **по позициям** A–T (остаток = сумма H–P,
  отдельно H, Q+R, S, T) и проверяет только маркеры «Артикул / Кластер / Склад». Это исключение
  из правила «по имени»: при смене формата Ozon проверить позиции. Кластер склада обновляется
  из отчёта.
- **S4 себестоимость.** Только товары из справочника. Загрузка задним числом пишет историю, но не
  трогает актуальную `item_cost`.

Ловушки:
- **P1/P2 — это не данные РНП.** Записи с источниками `upload_wb_spp` и `upload_ozon_coinvest`
  исключены из `recalc_spp_and_buyer_from`, поэтому загрузки РНП их не перезаписывают.
- **P1 WB:** внутри дня выбирается строка с самым поздним «Временем». Одинаковое время с разными
  значениями — ошибка. Несколько регионов на одну дату и артикул — ошибка.
- **P2 Ozon:** в файле нет времени. Разные значения на одну дату и артикул отклоняют импорт,
  одинаковые повторы объединяются. Загружаемая цена — «после акций», а не «Наша цена».
- **СПП 0 или пусто** (P1/P2) — товара нет: `spp_pct` и `buyer_price` = NULL, загружаемая цена
  сохраняется. Масштаб СПП в P1/P2 определяется **по величине**: текст с «%» или число > 1 делится
  на 100, иначе считается долей. Calamine не передаёт формат ячейки. Это расходится с общим
  правилом «не угадывать масштаб по величине».
- **P1/P2:** любая ошибочная строка отменяет весь импорт (показываются первые 8 ошибок). Артикулы,
  которых нет в `catalog_marketplace` для этого МП, пропускаются (`skipped_unknown`). Журнал —
  `mp_price_upload_log` (строка на каждую дату файла), а не `report_uploads`. Данные и журнал
  пишутся в одной транзакции.
- Старые шаблоны кабинета «Цены и скидки» (WB) и «Товары и цены» (Ozon), приложенные 14–15.09.2026,
  после 18.09.2026 не принимаются.
- **P3:** создаёт только известные артикулы (`catalog_items` ∪ `catalog_marketplace`, точное
  совпадение без `canon_article`). Цена округляется до целого. Некорректные значения отклоняют
  файл целиком. Это базовые цены, а не загружаемые цены продавца.
- **P4:** справочные колонки (уровни, статус) не читаются. Если шапка не распознала 12 месяцев,
  берутся последние 12 колонок строки. Артикул не канонизируется. `DELETE` и `INSERT` идут
  отдельными вызовами, без общей транзакции. Для Яндекса план принимается кодом (`MP_MAP`).
- **P5:** колонки берутся по позициям, а не по заголовкам. Наименование и категории — общие для всех
  МП: импорт для одного МП перезаписывает их у всех, пустая ячейка стирает категорию. Статус,
  менеджер и URL пишутся только выбранному МП. Новые артикулы создаются. Дубли канонического
  артикула пропускаются. После импорта сбрасываются кэши всех трёх деревьев РНП. Записи
  в `report_uploads` нет. Изменения `catalog_items` запускают пересчёт daily Pi по этим артикулам.

Ручные правки без файлов (`POST /api/prices/cell`, `/api/sales/plan_cell`, `PUT /api/catalog/items`)
доступны любому авторизованному. Это не отчёты, в реестр они не входят.

## 4. Общие правила загрузчиков

| Правило | Как в коде | Исключения |
|---|---|---|
| Колонки по имени заголовка | `_build_colidx` / `idx` по тексту шапки; списки допустимых вариантов (`*_HEADERS`, `OZ_NAME_ALIASES`) | S3 (позиции A–T), P5 (позиции A–H), P3 и P4 (артикул в 1-м столбце) |
| Канонизация артикула | `util.canon_article`: trim, схлопывание пробелов, гомоглифы, UPPER | S1 (только `upper`), R11 (свой `_canon`), P3 и P4 (только `strip`) |
| Пакетная запись | `INSERT` батчами по 100 (`loader_core`, R1/R5/R10), `UPDATE … FROM (VALUES …)` для `PRESERVE_COLS`, `db.execute_values` (батч 500, у прямых цен 1000), `executemany` (S1, S4, R11) | R2: построчные `UPDATE` по SKU |
| Перезапись дня без потери чужих полей | `PRESERVE_COLS` в R1, R5, R10: значения читаются до `DELETE` и возвращаются `UPDATE`-ом | R10 не восстанавливает строки, которых нет в новом файле |
| Транзакции | В `upload_router` на загрузку открывается отдельное соединение psycopg без autocommit, загрузчик сам делает commit/rollback. Новые артикулы коммитятся раньше основных данных | P1/P2 — одна `db.transaction()`; P4 и P5 — несколько независимых вызовов |
| Журнал `report_uploads` | Запись «В ПРОЦЕССЕ» → «OK» / «ОШИБКА…»; `period_kind`: `weekly`, `monthly`, `daily`, `ads`, `reviews`, `competitors`, `wb_daily`, `wb_reviews`, `wb_ads`, `wb_pi`, `ya_daily`, `ya_stock`, `stock`, `wb_stock`, `ozon_stock`, `cost` | P1/P2 пишут в `mp_price_upload_log`; P3, P4, P5 журнала не ведут |
| Кто загрузил | `upload_router._set_uploader` выполняет `set_config('app.uploader_id', id)` на соединении. Колонка `report_uploads.uploaded_by_user_id` получает значение через DEFAULT `NULLIF(current_setting('app.uploader_id', true), '')::int` | При ошибке `set_config` значение остаётся NULL |
| Просмотр журнала | `GET /api/upload/history?kind=…`: `wb_stock` и `cost` — любой авторизованный, остальные — только admin | Для `ozon_stock` (S3) отдельного `kind` нет, видно только в `all` |
| Сброс кэша | `cache.bump(namespace)` после записи: Ozon (R1–R4) → `rnp_sales_tree`; WB (R5–R9) → `rnp_sales_tree_wb`; Яндекс (R10, R11) → `rnp_sales_tree_ya`; S1 и P5 → все три | MPPROFIT, S2, S3, S4, P1–P4 кэш не сбрасывают: их разделы его не используют |
| Ограничения прямых ценовых импортов (P1/P2) | Файл ≤ 25 МиБ (проверка в эндпоинте → 413 и в парсере), распакованный XML ≤ 150 МиБ, ≤ 4096 элементов ZIP, без пароля, ≤ 20 листов, ≤ 64 колонок, ≤ 200 000 строк на лист, ≤ 2 млн ячеек всего | Только `price_upload.py`. У остальных загрузчиков таких ограничений нет |

Кэш хранится в памяти процесса (`app/cache.py`, TTL 1 час). При нескольких воркерах uvicorn
`bump` сбрасывает только свой процесс, остальные обновятся по TTL.
